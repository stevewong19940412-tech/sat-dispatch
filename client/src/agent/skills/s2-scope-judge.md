# 覆盖范围判定

## 这一步解决什么

**每个任务都要先回答一个问题：这颗星一次过顶能拍完吗？**

- 能 → 不拆，1 个任务 1 张单
- 不能 → 才拆单，每个条带一个独立任务

⚠️ **不要一上来就按幅宽切条带**。这是之前的错误做法：把「石景山区」这种小区块也切成 2 条带，派了两张单，用户看不懂为什么一块地要拍两次。

## 一条命令搞定（首选）

**不要自己去查卫星清单再手算**——那会反复翻页、很容易误判（曾出现「库里只有 20 颗旧星」的错误结论）。直接用：

```bash
dispatch scope '{"coords":[[39.95,116.15],[39.95,116.25],[39.90,116.25],[39.90,116.15]],"obsType":"optical","resolution":1}'
```

返回：

```json
{
  "region": {"widthKm": 8.5, "heightKm": 5.6, "maxEdgeKm": 8.5},
  "satellites": {
    "usableCount": 87,
    "widest": {"name": "JILIN-01 KUANFU 02B 2", "operator": "长光卫星", "swathKm": 150},
    "top5BySwath": [...]
  },
  "judge": {
    "needSplit": false,
    "reason": "区域长边 8.5km ≤ 最宽可用幅宽 150km（JILIN-01 KUANFU 02B 2），单星单次可完成",
    "estStrips": 0
  },
  "nextStep": "不需拆单：直接用 dispatch order-intake 建 1 个任务"
}
```

**直接把 `judge.reason` 和 `nextStep` 转述给用户即可**，不需要再补充计算。

## 命令背后的判定流程（供理解，不必手动执行）

### 第一步：量区域尺寸

从多边形算外接矩形，取长边和短边（km）。

### 第二步：查可用卫星的幅宽

按任务要求筛出可用卫星（观测类型匹配、分辨率满足），看它们的幅宽分布：

| 典型幅宽 | 代表卫星 |
|---|---|
| 12 km | 吉林一号窄幅、高分二号部分模式 |
| 45 km | 高分二号 |
| 60 km | 高分一号 |
| 90 km | 高分六号 |
| 150 km | 吉林一号宽幅 |

### 第三步：判断

| 条件（以最宽可用星为准） | 结论 |
|---|---|
| 区域长边 ≤ 最宽幅宽 | **单星单次可完成 → 不拆** |
| 区域长边 介于 1~2 倍幅宽 | **需侧摆跨带 → 保守按拆处理** |
| 区域长边 > 2×幅宽 | **确定需要拆** |

### 第四步（关键）：算一次候选确认

**判定不能只靠几何估算**，必须实际算候选验证：

- 估算「能覆盖」→ 跑一次候选（整块区域当 1 个任务）
- 候选返回有星覆盖整块 → **确认不拆**
- 候选返回覆盖不全 → 说明估算偏乐观，**转入拆单**

## 典型尺度对照

| 区域 | 长边 | 最宽幅宽 150km 时 | 结论 |
|---|---|---|---|
| 单座机场 | 5 km | 1 条带 | **不拆** |
| 石景山区 | 8.5 km | 1 条带 | **不拆** ✅ 实测 |
| 城区 30×30 | 30 km | 1 条带 | **不拆** |
| 北京市域 | 180 km | 需拆 | **拆（实测 6 条带）** |
| 京津冀 | 500 km | 需拆 | **拆 + 多星** |

> 注意：最宽幅宽取决于「满足分辨率要求的卫星」。要求 0.5m 时可用卫星会少很多，幅宽也会降到 12~45km 档，拆的条带数会显著增加。**必须用 `dispatch scope` 实测，不要凭这张表估。**

## 输出格式

```
【覆盖判定】
区域尺寸：{长边}×{短边} km
可用卫星幅宽：{最宽} km（{卫星名}）
判定：单星单次可完成 / 需要拆分为 N 条带
依据：{几何判断 + 候选验证结果}
```

## 硬性纪律

- **判定结论必须给数值依据**，不能只说「需要拆」
- 判「不拆」之前必须实际算过候选，不能凭估算
- 判「要拆」时，说明拆几条、依据哪颗星的幅宽
